# ADR-004: Persist analysis results with SQLite behind a repository

Date: 2026-11-16  Status: accepted

## Context
The midterm feedback noted the working slice "stores nothing," so the use case
stopped at logic and never reached storage. The final deliverable rewards a
complete "UI -> logic -> storage" path. The project is a solo, one-semester
effort, and any reviewer (partner or instructor) must be able to clone and run
it with no setup.

## Decision
Persist each completed analysis with **SQLite**, accessed only from the Data
tier through a `ResumeRepository` class. The Service tier depends on that
repository (injected in its constructor), never on SQLite directly, so the
storage engine could be swapped for PostgreSQL by changing only the Data tier.
SQLite needs no running server, so a clean clone runs with zero database setup.
The database file is git-ignored and created automatically on first use.

## Consequences
- **Positive:** the core use case now travels all the way to storage, and the
  result is findable (an `analyses` table), directly addressing the midterm
  action item.
- **Positive:** depending on a repository (not on SQLite) keeps the Service tier
  testable with an injected fake and makes the store swappable (DIP).
- **Negative:** no read/history UI yet — results are saved but not surfaced in
  the frontend. That is acceptable scope for this deliverable and could be a
  future enhancement.
